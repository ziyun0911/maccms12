================================================================================
maccms12 说明文档总览
================================================================================
maccms12 = 苹果 CMS v10（maccms10）整树升级版，核心框架实装 ThinkPHP 8.1.4
（多应用模式），由 maccms10-2026.1000.4056（TP5.1）迁移重写。本目录按官方
maccms10「说明文档」结构建立，内容以 maccms12 实际实现为准（API 方法、
数据库表、标签库均已实测核对）。

二、maccms12 版本与环境
--------------------------------------------------------------------------------
· 运行环境：PHP >= 8.0.2（composer.json 的 require.php；本机验证用 PHP 8.3.8）、
  MySQL 5.7/8.0+（本机 5.7.38）、Nginx/Apache/PHP 内置服务器均可。
· 入口文件：index.php（前台）、admin.php（后台）、api.php（接口/定时任务）、
  install.php（安装，已装后访问提示已锁；锁文件为 app/data/install/install.lock）。
· 数据库：maccms12（84 张表，前缀 mac_，含 mac_content_lang 内容语言表）；
  唯一配置来源 config/database.php（安装程序写入后会热更新进框架 Config，
  不存在第二份镜像）。
· 默认后台账号：admin（口令不写入文档，正式环境务必改密）；验证码开关
  app/extra/maccms.php → admin_login_verify（1 开 / 0 关）。
· 完整交付说明见项目根目录 README.md。

三、与 maccms10 核心差异（TP8 升级，功能/数据结构保持兼容）
--------------------------------------------------------------------------------
1. 目录结构：application/ → app/（模块 admin/api/index/install 按 TP8 多应用布局）。
2. 入口引导：四个入口重写为 TP8 引导并修复 PATHINFO 解析。
3. TP5 行为（application/tags.php 里的 behavior/*）迁为 TP8 全局中间件，
   声明在 app/middleware.php，实现放在 app/common/middleware/。除框架自带的
   SessionInit 外共 12 个，按执行顺序：SessionSameSite / Init / AddonInit /
   RequestSecurity / Begin / IpBlock / AntiScrape / MonitorRequest /
   PreviewLinks / SecurityHeaders / CookieSameSite / AdminAudit；
   application/tags.php 已删除。
4. 公共层 app/common.php 提供 mac_* 助手函数族（200+ 个顶层函数），承担原 TP5
   公共层职责：配置读写 mac_load_extra() / mac_arr2file() / mac_save_config_data()，
   模板与 URL mac_tpl_file() / mac_url()，输出 mac_echo() / mac_jump() 等。
   （注：本文旧版在这里列的 mac_config_set()、model()、THINK_VERSION 三个「兼容层」
   在当前代码里并不存在，属笔误，已按实际函数改写。）
5. 数据库配置单一来源：config/database.php（TP8 connections 结构）。安装程序
   写完文件后会 include 进框架 Config 热更新，不再保留 TP5 时代的第二份镜像。
6. vendor 保持 Composer 原样：三处 TP5 写法已改为 TP8 原生调用，不再有 vendor 补丁，
   因此 composer update 之后无需任何重打补丁步骤（清理记录见项目根 README.md）。
7. 清理项：删除 behavior 惰性代码、theme-request-form/、tests/、storage/、
   app/tags.php；static_new/ 已并入 static/（全库 0 处 static_new 引用）。
   根 route/ 目录并未删除，只剩 route/addons.php（插件统一路由
   addons/:addon/:controller/:action → app\common\addon\Dispatcher@run），
   由 app/index/route/addons.php require 复用；前台 rewrite 规则在
   app/index/route/rewrite.php，两者不要混为一谈。
8. 后台视图与控制器里的 application/ 路径已全部改为 app/（迁移时一次性改过 352 处；
   本次复查 app/admin/view/ 下已 0 处残留，剩下的 application/json 等是 MIME 类型）。
   模板（template/）与前台标签语法完全兼容 maccms10，可无损复用。

17. 【2026-10-26 跳转/提示页的三份副本与 page_404 的真实链路】
    承接说明 16，把 app/index/view/public/ 下最后两份残副本（jump.html、msg.html，
    内容都是 v10 时代的「网站维护中」页）一并删除；同轮把跳转页的解析链彻底查清：
    - Jump::jump()（app/common/controller/Jump.php:43-57）先读 app.dispatch_success_tmpl
      /dispatch_error_tmpl：后台入口拿到的是 config/app.php:65-66 的绝对路径
      app/admin/view/public/jump.html，is_file() 为真 → display(文件内容)；前台入口被
      Init 中间件（app/common/middleware/Init.php:120-125）改写成相对串 public/jump，
      is_file() 为假 → fetch('public/jump')，按当前 view_path 落到主题目录。
    - All::page_error()（app/common/controller/All.php:375-393）用
      label_fetch('public/' . $GLOBALS['config']['app']['page_404'])，page_404 是后台
      「网站参数」里的自由文本（app/admin/view/system/config.html:850），本机当前值 404。
      因此 template/default/html/public/404.html 与 …/public/msg.html 都是活的：站长把
      page_404 填成 msg 就会渲染主题那张 msg，删主题副本会直接把 404 页打挂。
    - 结论：只有 app/<模块>/view/public/ 下的副本是死的。前台 view_path 恒为
      template/<主题>/html/（Init 里置空的分支只在 admin 且主题目录缺失时触发），所以
      这两份永远不会被解析；api 入口沿用 config/app.php 的后台绝对路径，也轮不到它们。
    - 已实测（curl 指纹）：/index.php/user/oauth.html 渲染 weui_msg_jump +
      public-jump.css（主题 jump），/index.php/nopecontroller/nopeaction.html 渲染
      fail-page（主题 404），删除前后指纹一致、副本独有的 mac_msg_jump 与「维护中」
      全程零命中；临时把 page_404 改成 msg 后渲染的是主题 public/msg.html（weui_msg_jump
      + public-msg.css），改回 '404' 后配置文件与备份逐字节 cmp 相同。
    - 另记两处顺带发现：① app/admin/view/public/msg.html 同样零引用（后台
      只走 jump.html 那张），属同类孤儿，删不删等下一轮定；② page_404 未做字符校验，
      think-view 的 parseTemplate（vendor/topthink/think-view/src/Think.php:229）直接
      $path . $template 拼接、不过滤 ../，所以把该字段填成带 ../ 的值可以让 404 页渲染
      主题目录之外的 .html。② 已由说明 18 修掉。

18. 【2026-10-26 page_404 加字符白名单：保存侧拒绝 + 读取侧兜底】
    口径同站内其它地方（Update::step1 的文件名白名单）：只认字面量模板名
    /^[A-Za-z0-9_-]{1,64}$/，空值仍表示默认的 public/jump。
    - 保存侧：app/admin/controller/System.php::config() 在 pathinfo_depr 校验之后
      trim 再比白名单，非法即 return $this->error(lang('admin/system/config/page_404_err'))，
      不落盘。六个语言包各加一条 key（zh-cn / zh-tw / en-us / ja-jp / ko-kr / ru-ru）。
    - 读取侧：app/common/controller/All.php::page_error() 同一条正则再判一次，不合法
      直接回退 public/jump。这一道是真正的边界：think-view 不拦 ../，而修复前已经写进
      app/extra/maccms.php 的旧值不会被保存侧追认。
    - 深度纠正（说明 17 的说法太乐观）：../ 要从 template/default/html/public/ 爬出去才
      有效，三层只到 template/、命中不了文件；实测 '../../../../app/admin/view/public/jump'
      （四层）才真的渲染到后台那张跳页。
    - A/B 实测：用 git show HEAD 的旧 All.php + 上述四层 payload → 前台未登录请求返回
      HTTP 404 / 1811 B / <title>跳转提示 -…</title>（后台跳页被公开前台渲染）；换上本轮
      代码后同一 payload → 2019 B、weui_msg_jump + public-jump.css（主题 jump）、「跳转提示」
      零命中；两种情况都不打印绝对路径。合法值 'msg' 仍渲染主题 msg（925 B + public-msg.css）；
      不存在但合规的 'nosuchtpl' 走 renderFetch 的 404 回退（9733 B、fail-page），不会 500。
    - 后台 UI 实测（:8080 网站参数）：填四层 payload 点保存 → 吐司「404 页面模板名只能使用
      字母、数字、下划线和连字符（最多 64 字）」，app/extra/maccms.php 的 md5 与提交前一致
      （零写入）；填回 '404' 点保存 → {"code":1,"msg":"保存成功!"}，保存后的 maccms.php 与
      提交前逐字节相同（diff 0 行）。
    - 顺带一个坑：该页 __token__ 是一次性的，同一个页面连点两次保存，第二次会得到
      「请求失败」，与本轮校验无关，重新加载页面即恢复。
